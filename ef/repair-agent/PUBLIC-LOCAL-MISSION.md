# Execute the local Council repair

Run the Windows operations yourself as the local coding agent. Do not hand the user repeated diagnostic commands. Continue until the required live acceptance passes, or a precise credential, permission or external-service boundary prevents further authorized work. Save PROGRESS.md at the checkpoint path supplied by the launcher after each meaningful change and continue from it on the next launch.

1. Identify the installed Council paths, current Windows SID, configuration, runtime version, data roots, encrypted keys and exact process owners once. Do not print secrets. Check existing private handoff material if supplied. Do not assume a source checkout equals the running installation.
2. Preserve uncommitted work. Stage a pinned candidate release separately from stable member data. Make and verify a rollback copy of Council code/config and a consistent snapshot of saved data. Keep DPAPI keys encrypted and separate from portable exports.
3. Compare the included patch with the installed source before applying it. Prevent member runtimes from importing the host's legacy station. Restore or migrate the original owner's station only after verifying the member identity and stopping its exact Council writer. Do not overwrite an active store, erase locks or seed every member from a host save. An EPERM rename error requires checking the actual writer and permissions.
4. Preserve the selected local model and endpoint from installed configuration. Run Verify-Local-Council.mjs with those explicit values. Then require an actual harmless file write/readback through Council's registered tools, real tool-call receipts and matching bytes. Text claiming to perform an action is insufficient.
5. Verify a fresh launch from the configured issuer, its ticket/key agreement, the full UI and member isolation. Never bypass authentication or silently rotate a launch key.
6. Stage the matching gateway, start-recovery-gateway.ps1, Council-ProcessOwner.ps1 and Recover-Council.ps1 together. Use reviewed configuration and the original DPAPI identity. Register-Council-Startup.ps1 creates a current-user sign-in task and desktop Recover Council shortcut, with rollback/readback. Use Windows PowerShell 5.1. Resolve only positively identified old Council supervisors to prevent duplicate starts. Execute the registered task and verify it owns the running supervisor.
7. Test member crash, gateway crash, hung-but-live member and gateway, supervisor death, repeated recovery clicks, persistence and member isolation. Do not replay interrupted actions. Recovery must affect Council only. Reopen through a fresh issuer launch after a gateway session is lost.
8. Complete a real 65-minute browser idle interval, then verify a real local-model tool action and original saved data. Keep timestamps, process identities and useful memory/handle/log evidence. Do not replace elapsed time with a simulated timer or mask browser idle with polling. Run the timer in the background and continue authorized work while it runs.
9. Restore a saved checkpoint to an isolated target and compare conversation/station/artifact data. Keep code rollback separate from data restoration so newer work is not overwritten.
10. Record PASS, FAIL or BLOCKED separately for fresh launch/UI, actual model reply, actual tool action, saved data, member isolation, crash/hang recovery, scheduled-task execution, 65-minute idle/resume, backup/restore and actual reboot. Do not claim an observed reboot unless it occurred with authorization. Report complete only when the live gates are supported by evidence.

Scope: Council-only repair and restarts. Preserve unrelated stations and services. Do not restart/reconfigure Windows, Ollama, Docker, Cloudflared, NexusRENN or LiteLLM, use unrelated coding services, or merge/deploy a production branch without specific authorization. If an excluded layer is the proven blocker, finish safe work and identify the exact additional action required.

Keep Bitdefender enabled. Do not add broad exclusions or change PowerShell execution policy. If there is an actual security alert, inspect the specific event and verified executable, and use the normal approval process for the narrow necessary action. Do not evade quarantine or a security denial.

The tests/windows-supervisor.test.ps1 fixture is restricted to disposable GitHub runners. Never set GITHUB_ACTIONS=true on a user's PC to bypass that restriction. Use the installed live acceptance described above instead.
